# Campus Lost & Found

Vanilla-JS hash-routed SPA (HTML, CSS, Vite) backed by an optional Flask + SQLite API. Items live in SQLite (`backend/lost_found.db`) via `http://127.0.0.1:5000`; when the backend is down, the app falls back to the 14 built-in demo items for individual detail pages (`#/item/itm-*`). Homepage stats, listings, and recent items always reflect real database records — an empty DB shows zero counts. localStorage keeps only theme/visited plus a returned-overlay for demo items. Auth required for creating listings and reporting.

## Commands

- `npm install` — install deps (Vite + jsdom for smoke test)
- `npm run dev` — dev server at http://localhost:5173 (proxies `/api` and `/uploads` to Flask at 127.0.0.1:5000 via `vite.config.js`; same-origin, so session cookies work without CORS pain)
- `npm run build` — production build to `dist/`
- `npm run preview` — serve the production build
- Backend: see `README_BACKEND.md`; quick start is `.venv\Scripts\python.exe backend\app.py` (venv lives at the project root). Flask serves on port 5000 with debug auto-reload.
- `node scripts/smoke.mjs` — headless E2E (jsdom + vite ssrLoadModule): boots the real SPA in sixteen phases (A–P) against the LIVE Flask server — demo fallback on empty DB, refresh persistence of the demo returned-overlay, full SQLite flow (API-seeded items, mark-returned via PUT), fresh-session persistence, logout navigation, login redirect, category validation, owner-only edit/delete, prohibited-listing safety, university field (create/edit/filter/ownership), My Listings page (ownership isolation, mark-returned), advanced search/server-side filters (category/location/days/university/type/search combinations), admin system (role enforcement, user management, listing moderation, audit logs, blocked accounts), report listing system (submit reports, duplicate protection, admin moderation, resolve/dismiss, listing removal, audit logging, report counts, UI indicators), smart match system (lost↔found matching, notifications, dismissals, admin match stats), and claim this item workflow (claim found items, owner accept/reject, claimant notifications, duplicate prevention, privacy, admin stats) — asserting content and zero console errors. Requires an EMPTY items DB for phase A; it wipes/seeds/cleans item rows itself (back up `backend/lost_found.db` first if you have real data). Phase L wipes all items via Python subprocess before running. Run with the same Node used for dev (`node`, not npm wrappers; use `npm.cmd` under PowerShell execution policies).

Note (Windows): after installing Node via winget, existing shells keep a stale PATH. Prepend it before running npm/node:
`$env:Path = "C:\Program Files\nodejs;$env:Path"`

## Architecture

Hash-routed SPA. A single `index.html` shell hosts `<main id="app">`; `src/main.js` parses the hash and swaps views. All data access is async now — views render an instant shell (skeletons), then hydrate from the store facade.

Routes (`#/`):
- `/` home (shell hydrates stats/recent/categories async)
- `/lost-items`, `/found-items` — filtered listings
- `/items?q=&category=&status=&location=&days=&sort=&type=&university=` — browse-all / search results (`q` maps to backend `search`; category/location/days/type/status/university are server-side filters; sort is client-side over fetched results)
- `/my-listings` — owner's own listings (requires login, `?mine=1` server-side filter; guarded by session)
- `/item/:id` — detail (numeric ids = SQLite rows, `itm-*` = demo deep links)
- `/report?type=lost|found` — report form (POSTs to backend)
- `/admin` — admin dashboard (requires admin role; tabs for dashboard stats, listing moderation, user management, audit logs)

Module map:
- `src/main.js` — router + chrome wiring (theme toggle, mobile menu, search overlay, report dropdown, scroll effects, global delegation for mark-returned `[data-return-id]`, retry `[data-retry]`) plus auth UI: `authModal()` (login/signup), navbar `updateAuthUI()`, `verifySession()` on boot. `clf_user` in localStorage is ONLY a display cache — the real session is the Flask cookie; `verifySession()` reconciles them via `GET /api/auth/me`. Logout always navigates to `#/`.
- `src/js/api.js` — single API config (`BASE_URL`: `window.__API_BASE__` override for the smoke harness, otherwise relative `/api` so requests go through the Vite proxy same-origin; all calls send `credentials:'include'`): `ApiError` (status 0 = network failure, friendly messages), `request()` wrapper, `mapItem()` (snake_case row → frontend item shape), `dataURLToBlob()`, items API (`listItems/getItem/createItem/uploadImage/markReturned`) and auth API (`register/login/logout/getCurrentUser`), advisory endpoints (`validateCategory`, `checkListing`), admin API (`adminStats/adminListUsers/adminUpdateUser/adminListItems/adminDeleteItem/adminLogs`), report API (`createItemReport/adminListReports/adminResolveReport/adminDismissReport`), match API (`getItemMatches/getNotifications/markNotificationRead/markAllNotificationsRead/dismissMatch`), claim API (`createClaim/getItemClaims/getMyClaims/acceptClaim/rejectClaim`)
- `src/js/store.js` — data facade: `fetchItems(params,{allowFallback})`, `fetchItem(id,…)` hit the API first and fall back to tagged demo items only when the result is empty/unreachable AND the request has no user search narrowing AND params are structural-only (`type`/`status`); homepage stats/listings always use real API data (empty DB = zero counts); `createReport(payload,photoData)` POSTs then uploads the image (upload failure still returns the created item); `setReturned(id)` PUTs to the API, falling back to a local overlay for demo ids (404/network); also `statusOf`
- `src/js/data.js` — categories, 14 demo items (`itm-101`…), and universities array (`UNIVERSITIES` with id/label pairs, `UNIVERSITY_LABELS` lookup, `universityLabel()` helper)
- `src/js/ui.js` — icon set, `nav()` helper, toasts, date utils, reveal-on-scroll, `confirmModal()`, bell icon for notifications
- `src/js/components.js` — item cards, SVG image generator, skeleton cards (`skeletonCardsHTML`), error banner (`errorStateHTML`, has retry button), empty/not-found states
- `src/js/views/` — one file per route view; all async-hydrated

localStorage keys: `clf_returned_items` (demo-only overlay), `clf_theme`, `clf_visited`, `clf_user` (auth display cache only). (`clf_user_items` is obsolete; the old save/favorites feature was removed.)

Backend contract: `GET /api/items?type=&status=&search=&university=&category=&location=&days=`, `GET/PUT/DELETE /api/items/:id`, `POST /api/items` (JSON payload fields `item_name, category, type, description, date, location, contact_number, email, additional_details, university`), `POST /api/items/:id/image` (multipart `image`), `PUT /api/items/:id/returned`, `POST /api/items/:id/report` (JSON payload `{reason, details}`); reports require login, one pending report per user per listing. `POST /api/items/:id/claim` (JSON payload `{proof_details}`, ≥10 chars); claims require login, found-only, not own listing, one active claim per user per listing. `GET /api/items/:id/claims` owner-only claims list; `GET /api/my-claims` claimant's own claims; `PUT /api/claims/:id/accept` owner-only accept (marks item returned, auto-rejects others, notifies claimant); `PUT /api/claims/:id/reject` owner-only reject (notifies claimant). PUT/DELETE and image upload are owner-only (`ensure_owner`: 401 anonymous, 403 non-owner/legacy NULL owner); deleting a returned item is blocked with 400. `GET /api/universities` returns `{success, universities: [{id, label}…]}`. `POST /api/categories/validate` `{title, description, category}` → rule-based advisory check (`backend/category_rules.py`, no external services) returning `{valid, suggested_category|null, confidence 0–1, message}`; never blocks creation and is skipped silently when unreachable. `POST /api/listings/check` `{title, description, category}` → content-safety gate (`backend/content_rules.py`) returning `{allowed, reason}`; a 400 is returned for prohibited content (motor vehicles except bicycles, living things, weapons) on both `POST /api/items` and `PUT /api/items/:id`; the report form pre-checks this before category validation. Auth: `POST /api/auth/register` `{name,email,password}` → 201 `{success,message:"Account created successfully.",user{id,name,email,role}}` (409 duplicate email), `POST /api/auth/login` → 200 `{success,message:"Login successful.",user{…}}` or 401 `Invalid email or password.` (403 if blocked), `POST /api/auth/logout`, `GET /api/auth/me` (401 when anonymous). Registration always assigns `role:'user'`; role is never assignable via register. Sessions: Flask signed cookies (`secret_key`, HttpOnly, SameSite=Lax — same-origin via the Vite proxy is what makes them stick). Passwords hashed with Werkzeug (`generate_password_hash`/`check_password_hash`). Responses are `{success, …}` JSON; errors are JSON `{message}`.

Admin endpoints (all require admin role): `GET /api/admin/stats` → stats object + recent_items + recent_users + pending_reports + total_reports + total_matches + high_matches + medium_matches + total_notifications + total_claims + pending_claims; `GET /api/admin/users` → all users (no passwords); `PUT /api/admin/users/:id` → update role/blocked; `GET /api/admin/items?type=&status=&search=&university=&category=` → all items with filters + report_count per item; `DELETE /api/admin/items/:id` → delete any listing (logged in admin_logs); `GET /api/admin/logs` → audit log entries; `GET /api/admin/reports?status=&reason=&university=` → report entries with filters; `PUT /api/admin/reports/:id/resolve` → mark report resolved; `PUT /api/admin/reports/:id/dismiss` → dismiss report.

University field: stored as `university TEXT NOT NULL DEFAULT 'other'` (10 valid IDs: `mdu`, `du`, `kuk`, `pu`, `amity`, `lpu`, `cu`, `gju`, `mau`, `other`). Backend validates on create/edit (400 if missing or invalid). `GET /api/items?university=<id>` filters server-side (400 for invalid university). Existing rows default to `'other'` via the idempotent migration in `database.py`. Frontend: report form has a university dropdown; listing pages have a university filter; detail and card views display the university label.

Ownership: `items.reporter_id` (INTEGER → users.id, added by an idempotent startup migration in `database.py`; legacy rows keep NULL and are un-returnable by design). Creating an item requires a session — `reporter_id` is always taken from the Flask session, never the request body. `PUT /api/items/:id/returned` is server-side enforced: 401 anonymous, 403 non-owner (`"Only the user who reported this item can mark it as returned."`). Serialized items carry `is_owner` (bool, per-session) so the frontend can hide the button; demo-fallback items keep the localStorage overlay behavior. Smoke suite uses a persistent `smoke.owner@clf.test` account (register-or-login) so its seeded items are owned.

Returned flow: detail button (`data-return-id`) opens `confirmModal()`, then main.js awaits `setReturned(id)` → success toast → re-render refetches effective status. Demo items flip via the localStorage overlay; API items persist in SQLite.

Item images: generated SVG data URIs per category as fallback; report-form photos are canvas-compressed (~1000px JPEG data URL) and uploaded to the backend (`uploads/`).

Admin system: `users.role` column (`'user'` default, `'admin'` for admins); `users.blocked` column (0/1). All admin endpoints (`/api/admin/*`) verify role server-side via `ensure_admin()`. Admin dashboard (`#/admin`) shows real database stats (total users/listings, active/returned/lost/found counts, recent items/users). Listing moderation: admin can search/filter/delete any listing with confirmation. User management: admin can view all users, change roles, block/unblock accounts. `admin_logs` table records admin actions (admin, action, target_type, target_id, details, timestamp). Registration never assigns admin role; admin promotion is done via direct DB update or admin API. The `GET /api/auth/me` and login responses include `role` in the user object; the frontend caches it in `clf_user` localStorage and shows/hides the Admin navbar link accordingly.

Report listing system: `reports` table (listing_id, reporter_id, reason, details, status, resolved_at, resolved_by) with indexes on listing_id, reporter_id, status. `POST /api/items/:id/report` creates a report (requires login, one pending report per user per listing enforced server-side); `GET /api/admin/reports` returns all reports with optional status/reason/university filters; `PUT /api/admin/reports/:id/resolve` and `:id/dismiss` update status (admin only). `serialize()` includes `report_count` and `pending_report_count` per item; `reporter_id` is stripped from public API responses. `ensure_owner()` and `mark_returned` fetch raw `reporter_id` from DB directly to avoid the stripped field. Frontend: detail page has a Report button + modal (7 reasons, optional details); admin dashboard has a Reports tab with filterable table and resolve/dismiss actions. Admin listings table includes report count column. Admin stats include pending_reports and total_reports. Audit logs track report_created, report_resolved, report_dismissed.

Smart Match system: `match_notifications` table (listing_id, matched_listing_id, user_id, confidence, title, is_read, created_at, UNIQUE(listing_id, matched_listing_id)) and `match_dismissals` table (id, listing_id, matched_listing_id, user_id, unique on all three). `backend/matching.py` runs a deterministic scoring engine: category (+30), university (+25), title word-overlap (+25), description overlap (+10), location exact/partial (15/8), date proximity (5/3/1). Thresholds: HIGH≥65, MEDIUM≥40, LOW≥25, below=no match. Stop words filtered; min 2-char words only. `run_matchmaker(item)` fires on item create/update, finds opposite-type items, computes scores, creates `match_notifications` for both listing owners (INSERT OR IGNORE for dedup). Same-reporter_id pairs, returned items, and dismissed pairs are skipped. `GET /api/items/<id>/matches` returns owner-only matches (403 non-owner, 401 anonymous). `GET /api/notifications` returns user-scoped notifications with `unreadCount`; `PUT /api/notifications/<id>/read` and `PUT /api/notifications/read-all` mark read; `PUT /api/matches/<id>/dismiss` owner-only dismissal. Match notifications are deleted when either listing is marked returned. Admin stats include `total_matches`, `high_matches`, `medium_matches`, `total_notifications`. Frontend: notification bell in navbar with dropdown panel, mark-all-as-read; detail page shows possible matches section for owner with confidence badges and dismiss button. Phase O smoke tests cover matching scoring, notifications, dismissals, privacy, returned-item cleanup, and admin stats.

Claim This Item system: `claims` table (listing_id, claimant_id, proof_details, status, resolved_at, resolved_by, created_at, UNIQUE(listing_id, claimant_id)) and `claim_notifications` table (claim_id, user_id, listing_id, notification_type, title, item_name, is_read, created_at). `POST /api/items/<id>/claim` creates a claim (requires login, found-only, not own listing, proof ≥10 chars, one active claim per user per listing enforced via UNIQUE constraint); `GET /api/items/<id>/claims` returns owner-only claims list (403 non-owner, 401 anonymous); `GET /api/my-claims` returns the claimant's own claims with item details; `PUT /api/claims/<id>/accept` marks claim accepted, item returned, deletes match notifications, auto-rejects other pending claims for same item, creates claim notification for claimant (owner-only); `PUT /api/claims/<id>/reject` rejects claim, creates claim notification for claimant (owner-only). `serialize()` includes `claim_count` and `pending_claim_count` per item. `GET /api/notifications` merges match and claim notifications (prefixed IDs: `m` for match, `c` for claim); claim notifications include `notifType: 'claim'` and `claimStatus: 'accepted'|'rejected'`. Admin stats include `total_claims`, `pending_claims`. Frontend: detail page shows "Claim This Item" button for non-owners on found items (not demo, not returned); clicking opens proof-of-ownership modal (textarea, min 10 chars, submit button gated); My Listings page shows "Pending Claims" section for owner's found items with claim cards (claimant name, proof, Accept/Reject buttons with confirmation); owner sees pending claim count on item detail page with link to My Listings. Phase P smoke tests cover: anonymous claim (401), owner self-claim (blocked), short proof (rejected), valid claim (created), duplicate prevention, claim visibility (owner-only, 403/401), accept/reject authorization, accept → item returned + match cleanup, reject → item active, claimant notifications (accepted + rejected), notification read, re-claim after rejection (blocked), admin stats, UI (claim button visibility for owner/non-owner/lost-item, My Listings claims section).

The root-level `node.js` file is an unrelated empty leftover — do not touch it.
